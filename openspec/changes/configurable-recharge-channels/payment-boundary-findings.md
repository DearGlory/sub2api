# 第二轮前置核查：支付边界与协议证据

状态：静态核查。未修改业务代码，未部署，未访问真实商户后台或发起付款。来源与目标提交沿用 `design-interview.md` 记录的基线。

## 父助手已独立复核的事实

### 1. 当前来源查单不能直接支持目标的自动入账确认

- 来源 `backend/internal/payment/provider/epusdt.go:228-254` 的 `QueryOrder` 只填充 `TradeNo` 和 `Status`，没有金额。
- 目标 `backend/internal/service/payment_order_lifecycle.go:168-181,212-226` 对 paid 响应要求有效正数金额；第一次缺失会再查一次，仍缺失则退出，不据此履约。
- 因此不能通过“拿本地订单金额补成实收金额”来让测试变绿。该做法会消除验证而非修复协议缺口。
- 需要选择并核实实际商户协议：若有可信且可绑定同一交易的金额查询，适配该查询；若没有，签名通知和人工对账边界需要明确，不能宣称支持完整自动补单。

### 2. 公开项目文档补足了部分协议事实，但不是实际商户联调证据

查询到 GMWalletApp/epusdt 项目自有 API 文档和仓库文档。该项目确实公开了来源适配器使用的 GMPay 创建路径与 HMAC-SHA256 签名约定。因此“看起来是 GMPay 定制”不能被升级为“它没有公开协议”或“只能接原作者站点”。不同同名项目及实际部署版本仍可能不兼容。

项目公开文档将 `currency` 定义为法币币种、`amount` 定义为法币应付金额；`actual_amount` 是数字资产应付数量。其状态查询示例仍仅含交易号和状态。另有收银台初始化信息接口，但文档明确该接口不能单独确认当前支付状态，不能拿页面展示数据直接代替收款证据。

参考（项目第一方文档，实际部署契约待核验）：
- `https://www.epusdt.com/api/payment`：GMPay Request Parameters；GMPay Success Response；Cashier Initialization Data；Check Payment Status。
- `https://github.com/GMWalletApp/epusdt/blob/master/wiki/API.md`。

这些事实无需让用户凭猜测决定；下一轮只需用户指定拟接入服务，技术兼容性由实现方核验。

### 3. 用户身份透传与支付入账不是同一条授权链

- 目标 `frontend/src/utils/embedded-url.ts:16-42` 会把用户 ID 和传入的登录 token 放进外部 URL。
- `docs/ADMIN_PAYMENT_INTEGRATION_API.md:20-65` 描述外部系统通过管理员权限调用 `create-and-redeem` 入账；`:115-119` 把付款成功和充值成功分开记录并给出重试约定。
- 因此不能把“外部页能显示”视为“用户绑定可信且到账完成”。裸 `user_id` 不提供认证证明；同样不能未经核实就声称外部系统会验证本站 JWT。
- 现有订单 resume token 与登录身份断言不是同一概念。专用短期凭证需要接收方支持，不能仅修改本站就声称已打通。
- 是否沿用既有协议、采用外部独立登录或增加专用身份交接，应在明确外部收银台及其可控范围之后决定，不提前强推某一种接口。

### 4. 新 provider 的订单快照需要专门接入

目标 `backend/internal/service/payment_order.go:268-323` 为现有 provider 记录不同的商户／币种信息，没有 EPUSDT 分支。仅复制 `epusdt.go` 和工厂注册并不足以继承完整的金额、商户、网络和历史订单约束。实施设计须按实际协议列出可获得、应保存、应核对的字段；不能要求对方回传协议本就没有的字段，也不能把缺失字段当作验证已通过。

### 5. 退款和迟到付款必须独立定义

- 来源 `backend/internal/payment/provider/epusdt.go:326-328` 明确不支持自动退款。
- 目标 `backend/internal/service/payment_fulfillment.go:178-214` 允许取消订单恢复为已付；过期订单使用 `UpdatedAt` 与恢复窗口比较。
- `payment_fulfillment.go:217-238` 对超过窗口的过期付款只记录审计，不自动履约。
- 这不等于已证明该规则适配所选网关的链上确认延迟。待实际网关确定后再确认退款入口、迟到款、少付／多付和人工处置，不暗改所有现有 provider 的规则。
