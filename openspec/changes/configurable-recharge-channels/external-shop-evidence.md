## 必须保留的业务区别

这份商品文案支持“购买后取得卡密，再到指定站点兑换”的理解，不支持“支付完成即由店铺自动给当前 Sub2API 用户入账”的结论。

共享知识库《GloryCode公网入口直连newapi》将上述域名记录为 new-api 入口。该笔记是部署背景而非本轮实时路由探测；结合商品文案，足以要求核实卡密归属，仍不足以声称卡密必然不能用于 Sub2API。当前没有真实卡密，也没有进行任何兑换测试。

若采用买卡后手动兑换的设计：

- 本站只提供外部商品页与清晰的“返回本站兑换”入口；无需把本站登录 JWT 或当前用户身份交给店铺。
- 店铺发货的必须是目标 Sub2API 系统可兑换的余额码；是否由运营更新对应商品与库存需要用户确认，未经授权不改外部店铺。
- 新增入口的文案不能承诺付款即到账；余额以本站兑换成功为准。
- 这不会改写 USDT 的内置订单回调入账方案，两条链路分别验收。

## 嵌入限制核查

浏览器中对同一公开店铺 URL 作匿名 GET，返回 HTTP 200，响应未读到 `X-Frame-Options` 或 `Content-Security-Policy` 头。这仅排除了该次响应显式声明这两种限制的证据，**不代表跨域嵌入、浏览器第三方存储、支付跳转或微信内置浏览器已经验证可用**。

真实验收仍需在目标站点的 origin 中嵌入页面并完成只读交互检查；“新窗口打开”入口始终保留。外部页面内部样式不受本站 CSS 控制，本站仅保证入口、容器、说明及兑换引导保持既有风格。
