# 可配置充值能力：汇总契约草案

状态：业务决定已确认，本地实施进行中。此文件保留设计过程，最终配置与多网络边界以 Q20/Q21 确认及下文网络协议补充为准；不是完成或发布报告。实际进展及验收缺口见 `integration-progress.md`。

## 一、最终用户看到什么

### 外部购卡

- 保留现有内置充值、订阅，不复制来源项目替换订阅入口的行为。
- 在充值页面增加独立的外部购卡 tab；名称、地址和购买／兑换说明可在支付设置里维护。
- 默认嵌入指定综合店铺，并始终保留新窗口打开和返回本站兑换入口。
- 只提供买卡展示与兑换引导，不向外部页传本站登录 token、用户 ID 或完整本站页面地址；不读取跨域页面判断支付成功。
- 页面文案清楚写“购卡后返回本站兑换”；不承诺付完款就自动加当前用户余额。
- 外部页独立开关，默认关闭；内置支付关闭而外部购卡启用时，用户仍能看到购卡入口，但内置下单接口保持关闭。
- 普通用户仍需遵守现有登录、简易模式和后台模式约束，不借此放开整个后台或匿名内置下单。
- 店铺需实际发放 Sub2API 可用的余额兑换码。已读公开商品指向原站，这属于启用前运营核对，本次不修改店铺商品和库存。

### USDT 余额充值

- 内置充值中增加 USDT；用户显式选择管理员开放的网络，再填写 USD 计价的充值金额。
- 同时显示订单基数、本站手续费与预期增加的余额；实付 USDT 数量由 GM Pay 网关报价，不硬写 USD=USDT。
- 多网络共享本站的 USD 计价、独立充值到账倍率和手续费，首版不叠加既有充值赠送阶梯。
- 网关支付页用现有的支付跳转／等待支付 UI，样式延用目标项目，不复制 Signal Console。
- 只允许余额充值；前端不提供 USDT 订阅入口，后端也拒绝直接构造该订阅请求。
- 合法签名通知到账后按原订单幂等入账。回调缺失时等待网关重试或运营重发；页面回跳和状态查询不单独加余额。
- 关闭本地付款页面不代表取消了网关订单，也不能撤销已经发出的链上转账；提示用户不要对关闭／过期的订单继续付款。
- 对订单取消／到期后的有效收款只在固定宽限期内自动入账。默认宽限 30 分钟、后台可改；从有效期结束或取消时刻的较早者起算，旧订单截止点不会被重投、后台操作或新配置延长。
- 超过宽限的已验证款项显示待人工核对；用户收到明确提示而不是“已到账”。
- 本系统不开放 USDT 自助／自动退款；退款联系客服后由运营在系统外核对处理。

## 网络协议补充（用户已确认边界）

官方固定版本核查确认：用户选择网络后，收银台仍可通过 `POST /pay/switch-network` 切换资产／网络；切换不同目标可能创建子单，成功后通常归并回父单并以父单标识回调。回调没有 `network`，所以本地只能保存 `requested_network`，不能声称 `settled_network` 已验证。用户接受：签名、商户、订单、金额和 USDT 资产均匹配但网络无法证明时进入人工核对；不把网络选择伪装成网关锁网。


1. 创建时冻结用户、订单号、USD 基数、手续费、本站到账额度、商户实例、选中网络、计价与资产、有效期和宽限规则。配置变更只作用新单。
2. 网关创建响应必须与原订单绑定；保存上游交易标识和受限支付 URL，不能收到任意 URL 就导航。
3. 验证回调签名及商户；原订单号／上游交易号绑定正确，法币金额与原应收一致，付款资产确为 USDT；协议没有 network／currency 时使用原始创建绑定且不声称二次独立核对到缺失字段。
4. 有效且在自动入账时限内的首次成功通知进入现有幂等履约；重复、并发通知不能重复增加余额。
5. 有效但超过时限的通知持久化最小必要证据后标记待核对，正常确认通知接收，避免把重复投递当新支付。审核记录不保存密钥、签名原文或登录凭据。
6. 无效签名、商户／订单／金额／资产不匹配的通知不增加余额；只给出必要诊断且不能通过人工确认按钮绕过验证。
7. 管理员可筛选待核对，查看订单、原规则、交易号与核对原因；确认或拒绝必须填写备注并记录操作者。只有有效匹配的款项才可确认按原单额度入账，确认动作原子化并可重试。
8. 已确认、拒绝、履约中、已完成、已退款的状态交互须以测试固定；不让重投重新打开已处理审核或对相同链上交易重复入账。
9. “重试履约”只重试已证实收款的原订单，不能变成绕过收款校验的管理员加款接口。

## 五、实施编排（方案确认后才启动）

### 阶段 0：父助手冻结合同

在目标生产主线最新可验证提交上建立独立功能 worktree，不直接在生产主线或来源仓库改业务。父助手重核分支、dirty 状态和最新主线，保留访谈文档。读取 `go.mod`、实际测试依赖与仓库约束；准备每条写入工作流的独立 worktree 和依赖。

父助手唯一拥有：配置／DTO／端点合同、金额／网络／状态定义、SQL 及 Ent 迁移、共享 fixtures、依赖锁文件、汇总验收和冲突整合。先写合同测试并确认失败，再放出依赖实现，不让不同工作流自行发明同名字段。

### 首批独立工作流

| 工作流 | 写入责任 | 前置 | 首个可验收结果 |
| --- | --- | --- | --- |
| A 适配器与协议测试 | 新 provider 与对应测试，工厂／payment types 由合同主责协同 | 已冻结 provider 能力和网络／回调契约 | TLS 测试网关下真实 HTTP 下单／签名／通知失败与成功、无金额查询不触发补款 |
| B 外部购卡功能 | 外部购卡组件、独立配置保存读取、CSP、侧栏与路由中该功能约定范围 | 冻结配置与入口可见合同 | 内置支付关、外部页开情况下可读与可展示；不传 JWT；嵌入失败可新窗口 |
| C 订单与审核 | USDT 计价、快照、时限、审核与履约以及相应 handler/service 测试 | 父助手先提交数据合同及必要迁移 | 宽限边界、并发回调、超时审核、重复确认不重复入账 |

三条使用独立 worktree；共享文件按合同拥有者分块或串行整合，禁止直接在同一 checkout 并行写入。不得复制来源项目整个 payment handler/service 以覆盖目标安全补丁。

### 第二批依赖工作流

D 由独立工作流接 USDT 管理表单、选网用户流程、订单审核 UI、双语文案与组件测试。依赖配置 DTO、服务端网络列表、报价和审核 API 的已验证合同；不等待实现临时猜字段。

E 由独立审查工作流按假设检查边界：外部 URL 身份泄露、状态查询冒充收款、金额和币种混淆、审核绕过、网络切换绑定、宽限重置、老渠道回退。输出具体路径、可复现实例和证据，不自行部署。

合并顺序：共享合同与迁移 → A/C 后端 → B 独立入口 → D 用户及管理 UI → E 独立审查 → 父助手在整合提交上重新跑全部相关测试和真实浏览器检查。未授权前不 commit/push/release；实施工作流若需要 commit handoff，先在最终执行授权中明确。
